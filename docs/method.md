# 怎样学，才算学会

理解内核的关键是建立可检验的模型。先知道对象和职责，再顺着一个事件追踪，避免只背函数调用表。

## 一次学习的五步

1. **预测。** 在运行前写三句话：应该看到什么、依据是什么、什么现象会推翻它。
2. **运行。** 保留命令、输出、输入数据和版本，不只保留成功截图。
3. **追源码。** 每次只追一条路径，先锁定 1–3 个核心对象和状态变化。
4. **解释。** 用“谁持有对象、谁改变状态、谁负责释放、在哪个上下文”来组织答案。
5. **验收。** 改一个条件重做，并在不看笔记的情况下口述因果关系。

## 读源码的顺序

先看外部行为和接口，再找对象定义、调用入口与关键分支，最后看实现细节。函数名和字段会随版本变化；搜索实际源码，不把站点中的路径当成所有内核版本的固定答案。

```bash
# 在你自己的内核源码目录执行
# 同时记下便于阅读的版本和精确提交号。dirty 后缀提示工作树有本地修改。
git describe --always --dirty
git rev-parse HEAD
# 先定位任务结构，再找唤醒和调度入口。保留行号，便于回到同一版本上下文。
rg -n 'struct task_struct' include/linux/sched.h
rg -n 'try_to_wake_up|schedule\(' kernel/sched
```

先画 `task → mm / files / signal` 这样的对象图，再画 `read → 等待 → 唤醒 → 再运行` 这样的时序图。不要把“调用过某函数”直接等同于“该对象已经完成某状态转换”。

## 如何记录不确定性

给结论标注层级：用户 API 的语义、通用 Linux 机制、某个内核版本实现、某块板的实际观测。比如“线程共享地址空间”属于模型；“这份 BSP 在这里调用某函数”需要提交号；“这个时延来自 DMA”需要时间线证据。

尚未验证的推断写成假设。观察到没有 trace 事件，可能是功能未开启、权限不足、缓冲区丢事件或路径未发生，不能直接断言机制不存在。

## 把一个疑问变成两次能区分结果的操作

在 L02 读到「管道里没有数据」，还需要问：写端是否开着？下面使用非阻塞读，让同一个终端立即显示两种结果。Python 调用的是 Linux 管道和 read 接口。

```bash
python3 - <<'PY'
import os
# 匿名管道一次返回读、写两个 fd。只把读端设为非阻塞。
r, w = os.pipe()
os.set_blocking(r, False)
try:
    # 写端仍开着且没有字节可读，这次读取会立即报 EAGAIN。
    os.read(r, 1)
except BlockingIOError:
    print("writer open: EAGAIN")
# 关闭唯一写端。缓冲区一直为空，下一次读应当得到 b''，即 EOF。
os.close(w)
print("writer closed:", repr(os.read(r, 1)))
os.close(r)
PY
```

第一行的 `EAGAIN` 表示现在没字节可读，仍有写端能送数据。第二行的 `b''` 表示读到了文件结束（EOF）。两次读取间只关闭了最后一个写端。换成阻塞读，第一次调用会等，所以必须安排另一线程或进程写入或关闭写端。[pipe(7)](https://man7.org/linux/man-pages/man7/pipe.7.html)

**这段代码测出了调度延迟吗？** 它验证了接口返回条件。要量等待者何时重新获得 CPU，还需要唤醒和切入这两个时间点。

**另一台机器给出了不同的耗时或线程号，还算复现吗？** 本例中只要管道状态与读取结果的对应关系相同，结论便得到复现。研究耗时时才需要把时钟、负载与采样口径也纳入比较。

## 结果对不上时从哪里查

先核对输入和对象，例如打开哪个进程的 `/proc` 文件、管道另一端是否仍开着。再核对工具，例如采样时间是否在线程退出以后、板上的 `ps` 是否支持该选项。最后查实现，记录内核版本、配置与源码提交。把第一个不符合预测的步骤写进[实验笔记](notebook.md)，下一轮只改一个变量。
