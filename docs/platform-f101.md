## 第 37 周读一条真实的中断路径

从链接映射文件找到启动代码和异常向量设置。在 SDK 中查向量基址写入、trap 入口、汇编现场保存、IRQ 分发和选中外设的回调注册，把每一项记录到具体符号与文件。对照这版移植判断异常进入的特权级及使用的 CSR。回调签名和注册位置也能帮助你区分硬件中断处理例程、驱动工作任务与软件定时器服务任务。

从 SDK 选定的 FreeRTOS 配置查任务通知是否可用，确认该中断的优先级允许调用内核接口。沿中断结束路径找出此移植如何请求上下文切换。用同一构建的反汇编检查现场恢复与 trap 返回指令。

## 第 38 周测量响应

让接收任务用 `ulTaskNotifyTake` 等待通知。若 SDK 支持且回调确实处在可调用内核的 ISR 中，可在回调里记录计数并调用 `vTaskNotifyGiveFromISR`。按该移植的示例处理“更高优先级任务被唤醒”的标记。尽量使每次触发间隔足够长，先让前一次通知消费完成。任务醒来后记录读取到的通知值。成批到达时，通知取值的清零或递减语义会影响一次唤醒对应几个事件。[FreeRTOS 任务通知与等待语义](https://www.freertos.org/Documentation/02-Kernel/04-API-references/05-Direct-to-task-notifications/03-ulTaskNotifyTake)

先用同一时钟记录 ISR 和任务两个时间点，然后增加一个已知优先级、运行时间有限的任务，重复采样。两次使用相同外设、输入和周期。在采集结束后统一输出日志，避免同步串口打印扰动被测时段。分辨率仅为一个 tick 时，报告相同 tick 或相差几个 tick，并解释这对精度的限制。

## 手算一次“两个中断，一次任务唤醒”

ISR 是硬件中断进入后负责服务设备的例程。任务通知是 FreeRTOS 为指定任务维护的状态和值，可以把它用作事件计数。先在纸上构造一组输入：接收任务已阻塞，通知值为 0；两次 ISR 都调用 `vTaskNotifyGiveFromISR`，任务在第二次之后才执行。

| 时刻 | 发生什么 | 接收任务的通知值 |
| --- | --- | --- |
| T0 | 任务阻塞在 `ulTaskNotifyTake(pdTRUE, portMAX_DELAY)` | 0 |
| T1 | 第一次 ISR 发出通知，任务可以运行 | 1 |
| T2 | 第二次 ISR 发出通知，任务尚未消费 | 2 |
| T3 | 任务获得 CPU，等待函数返回 2 | 返回时清为 0 |

再把第一个实参改为 `pdFALSE`。同一组输入下，第一次取走一个通知，返回取之前的 2，剩下 1；紧接着再取会返回 1。超过一个事件时，这一区别决定你能否逐项消费。任务通知只保存计数；若要知道中断 A 对应哪个时间戳，仍需在驱动里给样本加序号并妥善保存。

**自测：任务恢复只打印一次，能判断按键只产生了一次中断吗？** 先看通知返回值和独立 ISR 计数，再核对去抖逻辑及采样溢出。如果始终没有通知，先用调试器确认回调是否执行、当时处于何种上下文，再核对通知目标句柄和正在等待的任务。串口输出放在任务中，采样结束后再打印。

## 延伸到显示驱动

把同样的 ISR 与任务观测方法用于板厂已工作的显示例程。先从面板配置查分辨率、像素格式和实际 stride（每行占用的字节数），计算单缓冲开销 `stride × 高度`，对照 map 文件、内存池及具体料号的 PSRAM。再追绘制、提交、传输完成和缓冲复用的位置。例如一个 800 × 480 的 RGB565 紧密排列缓冲区占 768000 字节，双缓冲需两倍空间。该算例用于检验计算，实际面板、对齐和缓冲个数以工程配置为准。标出哪一个完成信号允许上层重新写入这块内存。
