## 观测工具怎样分工

`strace` 用于系统调用边界，ftrace/trace-cmd 用于内核事件，perf 用于采样与性能线索，驱动日志用于状态与错误。工具可用性取决于内核配置、权限、符号与 tracepoint；不要求在未知 BSP 上全部启用。

先用 `available_events` 确认事件，再选择少量目标事件。trace 的开销、丢失事件、不同日志时钟和采样偏差都要记录。函数耗时包含等待或抢占的可能性，不能一眼认定都是函数在 CPU 上执行。

参考：[内核 tracing 文档](https://docs.kernel.org/trace/index.html)。初次操作只观察已有正常业务，重现故障时保证输入、负载和温度等条件可说明。

## 把“这帧很慢”变成可检验的结论

先从已有正常用例中选一个能贯穿提交与完成的标识，例如驱动请求序号。只按相近时间配对可能串帧；如果一批任务共享一次中断，保留批次关系。下面是假设的单请求时间线，时间戳来自同一单调时钟，单位 ms，供练习归因。

| 时刻 | 事件 |
| --- | --- |
| 0 | 用户提交请求 A |
| 2 | 驱动启动 A |
| 7 | 处理 A 的完成中断 |
| 8 | 等待线程变为可运行 |
| 14 | 调度切入该线程 |
| 15 | 线程返回用户空间 |

总时延 15 ms。启动到处理中断相隔 5 ms，可能同时含硬件运行和中断送达延迟；唤醒到线程切入相隔 6 ms，是已可运行后的调度等待。先针对后者做区分实验：固定输入、频率策略和采集事件，分别在空闲和有可控 CPU 竞争时重复采样。若后一段稳定变大而前一段相近，优先追调度。若 trace 有丢事件、时钟不一致或序号不清楚，该次样本不能用于分段归因。

**答辩对照一：** 谁在什么时候睡眠？从等待调用、`sched_switch` 的前一任务状态与随后的 `sched_wakeup`，核对同一 TID。中断可能只安排后续工作，真正通知等待者的也可能是工作线程。每次写出实际执行完通知函数的上下文。

**答辩对照二：** 怎样知道缓冲区可以复用？沿提交和完成路径找所有权交接，确认设备结束访问、必要的同步或 fence 已完成。IOMMU 负责设备地址转换，它的存在本身不能证明传输已结束。

**答辩对照三：** 找不到 IRQ 事件怎么办？先用同配置下的成功样本检验事件是否可见，检查设备是否轮询、IRQ 是否共享，再对照驱动状态与输出。迁移到另一颗 SoC 后须重新核对 IRQ、DMA 映射和电源依赖；线程唤醒与调度切入仍能用同样的证据区分。

## 最终报告结构

1. 问题与范围：输入、期望、实际、成功判据。
2. 环境与复现：板卡、源码 SHA、配置、固件、命令、原始日志位置。
3. 机制：任务、缓冲区、设备、IRQ、同步对象的关系图。
4. 时间线：提交、排队、执行、完成、唤醒、返回以及可观测空白。
5. 假设与实验：改变了哪个变量，排除了什么，仍不能断言什么。
6. 结论与改进：如有改动，解释为什么有效，并保留前后验证。

## 答辩问题

任务什么时候睡眠、谁唤醒它？硬件完成和用户态返回之间为何仍有延迟？缓冲区由谁拥有、何时可以复用？IOMMU 在哪里参与？更换 CPU 核型和更换 SoC 外设分别会改变哪些结论？如果没有中断日志，如何区分硬件未完成与观测缺失？
