# L13 · 全志平台的中断与时间线

**约 120 分钟起，按手头平台选一条路径。** V821、V861 使用 Tina Linux 上已工作的外设，F101 使用 FreeRTOS 上能控制的硬件事件。有两块板时，比较它们从中断到任务运行各经过了哪些步骤。

## 先写预测与对照

选一个能手动重复的输入，例如一组独立按键动作，或摄像头采集示例的一次固定长度运行。写下设备、驱动、预期计数、接收任务和时间单位。V821 先按[两核分工](platform-v821.md)确认外设由哪一侧驱动。V861 记录 [Linux 在线 CPU](platform-v861.md)。F101 沿[异常入口和任务通知](platform-f101.md)核实回调所在的上下文。

设计两个同长度观察窗口。窗口 A 保持空闲，窗口 B 执行约定操作。记录其他可能产生流量的服务。按键抖动、摄像头分块、共享 IRQ 或硬件批处理都可能改变“操作次数”和“中断次数”的关系。

## Linux 路径：找到计数变化最大的相关 IRQ

在可写目录内，终端 A 保存三个计数表。第一个十秒窗口保持空闲，第二个窗口用终端 B 执行外设操作，或在板上按键。每次保存时同时记下操作是否成功。

```sh
cat /proc/interrupts > irq-before.txt
sleep 10
cat /proc/interrupts > irq-idle.txt
sleep 10
cat /proc/interrupts > irq-active.txt
```

只挑与外设驱动相关的一行，分别计算每个 CPU 在两个窗口中的差值。根据驱动绑定、设备树的中断父节点、驱动请求 IRQ 的位置和表中名称核实身份。设备树里的硬件中断描述和 Linux 分配的 IRQ 号可能不同。如果活动窗口计数没有变化，先检查是否确有输入、驱动是否使用轮询、该外设是否属于实时核。

若镜像提供 `trace-cmd`，并且权限和内核配置允许，先用 `trace-cmd list -e` 核对事件。下面的命令在测试板上记录一个十秒窗口，窗口内从另一终端触发同一个已知输入。

```sh
trace-cmd record -e irq:irq_handler_entry -e irq:irq_handler_exit \
  -e sched:sched_wakeup -e sched:sched_switch sleep 10
trace-cmd report > active-trace.txt
```

在报告中按 IRQ 号、任务 PID 和 CPU 筛出候选事件。查看驱动是直接唤醒读者，还是先将完成事件交给 IRQ 线程或工作队列。仅有相邻时间戳时，把连接暂列为假设，再查驱动的等待队列或完成回调。缺少跟踪能力的镜像可以先提交计数对照和源码路径，标注调度延迟尚未测出。[Linux 事件跟踪](https://docs.kernel.org/trace/events.html)

## FreeRTOS 路径：测量 ISR 到任务恢复

1. 使用 [F101](platform-f101.md) 上已能复现的输入。测试开始前创建接收任务、保存其句柄，并在 SDK 许可的中断上下文启用通知。记录计时器频率、计数宽度以及时间戳读取方式。
2. 在 ISR 入口和任务恢复后各保存一个时间戳。用独立缓冲区保存两端数据，记录触发序号和通知计数。先按一次、等待消费、再触发下一次。若存在积压、按键抖动或缓冲区溢出，只配对能确认归属的样本。
3. 用同一个自由运行计数器计算时间差。无符号计数差按计数位宽处理回绕，采样间隔应短于一次完整回绕周期。时间差除以计数频率得到秒。若 SDK 只提供任务 tick，先验证它在所选 ISR 中的读取接口，再按 tick 报告。
4. 用相同输入重复至少十次，记录最小值、中位数、最大值和异常样本。比较 Linux 和 RTOS 时先对照不同事件的定义。这里测得的起点为软件观测到的 ISR 入口。测量物理引脚边沿到入口还需要外部时间基准。

## 把记录读成时间线

下面是简化的 Linux 教学样例，假定时钟可跨 CPU 比较，且驱动路径和同一笔输入的对应关系已经核实。时间以秒为单位，任务的 PID 是 42。

| 时间 | 记录事件的 CPU | 事件和关键字段 |
| --- | --- | --- |
| 1.000000 | 0 | `irq_handler_entry`，Linux IRQ 17 |
| 1.000012 | 0 | `sched_wakeup`，`pid=42 target_cpu=1` |
| 1.000031 | 1 | `sched_switch`，`next_pid=42` |

第一行表示内核开始调用中断处理函数。第二行由 CPU 0 记录，`target_cpu=1` 是目标任务的调度位置。第三行才显示任务被调度到 CPU 1。用后两行相减得到就绪到上 CPU 的间隔 19 微秒，首末两行相减得到 31 微秒。要量 IRQ 处理函数本身的时间，还要配对同 CPU、同 IRQ、同一轮事件的 `irq_handler_exit`。若该 CPU 的时间戳不能与另一颗核比较，先在同一核上取事件，或在 SDK 中核实 trace 时钟再重采。

**自测：F101 的 16 位向上计数器在 ISR 入口读到 65530，任务恢复读到 10，频率 1 MHz，相隔多久？** 若确认间隔短于一次完整回绕，计数差为 `(65536 - 65530) + 10 = 16`，即 16 微秒。这个结果包含了 ISR 入口到任务采样点之间的时间。若两端用不同计数器，应先同步时钟或改用同一计数器再算。
